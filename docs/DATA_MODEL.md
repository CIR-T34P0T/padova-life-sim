# Data model

Three layers: **persistent** (PostgreSQL, survives restarts), **replicated**
(Colyseus state, everyone in the room sees it while online) and
**server-only runtime** (in memory, never sent to clients).

Everything in this file is implemented, except the section marked
**Proposed** at the end.

## The character profile (canonical schema, implemented M4–M6)

The one in-code shape of a character profile is `CharacterProfile` in
`shared/src/profile.ts`, at profile version `PROFILE_VERSION` = 3. The server
assembles it from the tables below (`ProfileService`), sends it only to the
owner (`profile` message), and no other module defines its own copy.

| Field | Type and rules | Stored in | Who sees it | Who changes it, and how |
| --- | --- | --- | --- | --- |
| `characterId` | UUID, generated by the server | `characters.id` | Owner | Never; stable for the character's life |
| (owning account) | UUID, from the authenticated session | `characters.account_id` | Server only | Never; ownership comes from the session, never from a client |
| `displayName` | `sanitizeDisplayName`: Unicode-normalised, control characters and `<` `>` removed, spaces collapsed, cut to 20 characters, refused if under 2; not unique | `characters.display_name` | Everyone (`PlayerState.name`) | Set at creation; no rename yet |
| `ageCategory` | `child` \| `teen` \| `adult`; player characters must be `adult` (D-019) | `characters.age_category` | Owner | Set at creation only |
| `appearance` | `AppearanceConfig`, schema version 1 (see "Appearance config" below) | `character_appearance.config`, plus the M4 columns as a rollback projection | Everyone, as the replicated `look` string | The owner, through `updateAppearance`; validated strictly as a whole |
| `traits` | 0–2 distinct ids from `TRAIT_IDS` (`MAX_TRAITS` = 2) | `character_traits` | Owner (also in `life`) | Set at creation only |
| `profileVersion` | Integer; 3 today | `characters.profile_version` | Owner | The server, when it upgrades stored data on load |
| `createdAt`, `updatedAt` | ISO timestamps | `characters` | Owner | The server |

Creating a character takes a `NewCharacterInput` (`displayName`,
`ageCategory`, `appearance`, `traits`) checked by `parseNewCharacter`; any
other field a client sends (an id, an owner, a balance) is ignored. The title
screen lists characters as `CharacterSummary` (`shared/src/protocol.ts`:
id, name, look, traits, created and last played, read-only flag, notices),
never with life data.

**Deliberately not in the profile:** position (`character_state`) and the
life data (needs, skills, mood events, wallet, ledger), which have their own
tables, are loaded by `LifeService` and reach the owner in the `life`
message. Later systems attach to `characters.id` the same way, each in its
own tables, instead of growing the profile.

## Persistent (PostgreSQL, since M4)

Schema: `server/migrations/0001_identity_and_profiles.sql` (identity and
profiles, M4), `0002_life_simulation.sql` (traits, needs, skills, mood
events and money, M5) and `0003_appearance_config.sql` (the appearance
document, M6). One table per concern, so later systems (inventory,
relationships, jobs) get their own tables instead of growing one JSON blob.

**Money changes** (`applyMoneyChange`): one database transaction that locks
the wallet row (`SELECT … FOR UPDATE`, scoped to the owning account), checks
the request key, checks the balance, then updates the wallet and appends the
ledger row. Outcomes: `applied`, `duplicate` (same key: nothing changes, the
original result is reported), `insufficient_funds` (nothing changes) or
`not_owner`. Prices come from the server's catalogue (`CAFE_MENU`), never from
the client. Concurrent requests for the same wallet are serialised by the lock;
the CHECK constraints are a second line of defence.

**Wages** (`recordShift`, M7): when a shift's time is up, one database
transaction locks the wallet (scoped to the owning account), returns the
original payment if this shift id was already recorded (`duplicate`),
checks the character still has that job (`not_employed`) and has fewer than
the job's daily limit of shifts on that game day (`shift_limit`), then pays
the wage through the same ledger code as every other money change (key
`wage:<shift id>`) and writes the `work_shifts` row. Either both are written
or neither. A shift that ends early is never written, so it is never paid.
Wages come from the server's job catalogue (`JOBS`), never from a client.
Hiring (`hireCharacter`) and quitting (`quitJob`) are single owner-scoped
statements; quitting deletes the job row and keeps the shift history and
wages.

**University** (M8): enrolling (`enrolCharacter`) and counting a study
session (`recordStudySession`, only while enrolled) are single owner-scoped
statements. A completed lecture (`recordLecture`) and a completed exam
(`recordExam`) each run in one transaction that locks the character's
enrolment row (scoped to the owning account), so one character's records
never race. `recordLecture` returns `duplicate` for a lecture key already
recorded, refuses unless enrolled (not yet passed), then writes the row.
`recordExam` returns the original result for a sitting already graded,
refuses unless enrolled, counts the stored lectures, computes the grade with
`examGrade` from those counts and the academic level the server passes in,
writes the assessment and, with a passing grade, marks the course passed —
all or nothing. A lecture or exam that ends early is never written. Grades
are never sent by a client.

**Relationships, blocks, reports and the story** (M9, SQL in
`server/src/social/socialRepository.ts`): every call takes owners the
server resolved from sessions, and checks each (character, account) pair
before writing. A shared moment (`recordMoment`) locks the pair's row,
counts today's moments of that kind against the daily cap, writes the
moment, updates the score (at most 100) and drops all but the newest 20
moments — in one transaction. Blocking (`blockAccount`) and reporting
(`insertReport`) lock the acting account's row so their limits can't be
raced; reporting refuses a second report of the same account within 24
real hours and a sixth within an hour. `purgeReports` deletes reports older
than 90 days (the server runs it on start and hourly; `npm run reports` runs
it before listing). Story events (`addStoryEvent`) are written once per
event key.

**Homes and furniture** (M10, SQL in `server/src/housing/housingRepository.ts`):
every call is scoped by the owner the server resolved; each locks the
character's current home row first, then the wallet. Renting
(`rentRoom`) charges the first week through the ledger (key
`lease:<request id>`), ends a current home (its furniture into storage)
and starts the new one, in one transaction; the same request again returns
the same home (`duplicate`), also when two arrive at once. Weekly rent
(`chargeRent`) is paid once per home and week (key `rent:<home>:w<week>`)
and only when the balance covers it. `markOverdue` records when the grace
period started (kept on repeats). `moveCheaper` re-checks everything under
the lock (the week is due, the grace period is over, the money still isn't
there), ends the home as 'unpaid' and starts the dearest cheaper room whose
first week the balance pays (key `rent-move:<home>:w<week>`), or none.
Furniture is bought into a free spot of the current home (`buyFurniture`,
key `furniture:<request id>`; refused when the spot is taken or the
character owns 30 pieces), placed from storage (`placeFurniture`) and put
away (`putAwayFurniture`). Prices come from `FURNITURE`, never from a client.

**Migration 0002 for existing characters:** M4-era characters get starting
needs (80/80/80/70/70), a €100 wallet with a "Starting allowance" ledger row,
no traits and no skills. Its `down` section drops all six tables (destroys
life data; back up first).

**Migration 0003 (M6).** Adds `character_appearance.config`. Existing rows
keep `config` NULL and `profile_version` 2; the server upgrades each
character the first time it loads (profile version 2 → 3: the six flat
fields become an appearance config with the same body frame, the old skin
tone mapped onto the new continuous scale, hair style, hair and eye colour,
and the outfit split into top / outer / full outfit) and saves it. Its
`down` section sets version-3 characters back to version 2 and drops the
column; the M4 columns already hold the closest old look, so nothing is lost
that the M5 server could show.

**Migration 0004 (title screen, D-031).** Drops the unique index
`characters_one_per_account` and adds `characters_by_account (account_id,
created_at)`, so one guest profile can hold several characters. The limit
(3) lives in `PROFILE_CONFIG.maxCharactersPerAccount` and is enforced in
`createCharacterForAccount` inside one transaction that first locks the
account row. Its `down` section recreates the unique index; it fails, and
changes nothing, while any account has more than one character (delete the
extra characters deliberately first; nothing is deleted automatically).

**Migration 0005 (first job, M7).** Adds `wage` to the ledger's category
CHECK and creates `character_employment` and `work_shifts`. Existing
characters start without a job; nothing else changes. Its `down` section
fails, and changes nothing, while any wage was ever paid or any character
has a job (remove that data deliberately first; nothing is deleted
automatically).

**Migrations 0006–0008** (M8 university, M9 relationships and safety, M10
homes) create their tables; existing characters start without an enrolment,
relationships, a home or furniture, and 0008 gives every character comfort
70. Each `down` section fails, and changes nothing, while its tables hold
data (0008: any home or furniture, a rent payment, or a M10 story event);
0008's also drops the comfort column.

**Deleting a character** (`deleteCharacter`, title screen only, after the
player typed its name): one `DELETE FROM characters` scoped by the owning
account; appearance, position, traits, needs, skills, mood events, wallet,
every ledger row, the job and the shift history, homes and furniture cascade. The account, its credential and its other
characters stay.

**Deleting a whole guest profile** (`deleteProfile`, M12, D-046; title
screen only, after the player typed *delete*, and only while none of its
characters is being played): one `DELETE FROM accounts` for the session's
account (`deleteAccount` in `profileRepository.ts`). The guest credential,
every character with everything above that cascades from it, and every
block the account made or received go with it. Relationships cascade from
the characters, so the other player's side of a friendship goes too.
Reports the account made stay until they expire (90 days) with the
reporter set to null; reports about the account are deleted. Nothing about
the account remains except those anonymous reports.

**The title screen list** (`listCharactersByAccount`): the account's
characters, most recently played first (`character_state.updated_at`, which
every save touches), each upgraded and repaired like any load. Sent to the
owner without life data.

**Appearance config** (`shared/src/appearance/schema.ts`, version
`APPEARANCE_SCHEMA_VERSION` = 1). One JSON object:

```
{ v: 1,
  body:   { frame, build, height, shoulders, torso, legs, arms },
  skin:   { tone, undertone, freckles, mark, blush },
  face:   { shape, cheekbones, jaw, chin, forehead, eyeShape, eyeSize, eyeSpacing, eyeColour,
            browShape, browHeight, noseShape, noseWidth, noseLength, lipShape, lipFullness },
  hair:   { style, colour, hairline, facial },
  outfit: { top, topColour, pattern, bottom, bottomColour, full, shoes, shoesColour,
            outer, outerColour, glasses, headwear, headwearColour } }
```

Option fields hold catalogue ids (`shared/src/appearance/catalogue.ts`);
slider fields are numbers 0–1 with two decimals (meanings in `schema.ts`).
Strict validation for anything a player sends (`parseAppearanceConfig`:
every field present and valid, or refused naming the field, e.g.
`hair.style`); lenient repair for stored or replicated data
(`sanitizeAppearance`: out-of-range sliders clamped, unknown ids replaced by
defaults and listed). There is **no ethnicity, race, nationality or heritage
field** (D-029), and no life-simulation rule reads appearance (guarded by a
test). Choices that are covered by others (hair under a headscarf, top and
bottom under a full outfit) stay saved; `visibleLayers` decides what is drawn.

**Profile versus table versions.** `profile_version` describes the *shape
and meaning* of profile data and is upgraded in code on load
(`shared/src/profile.ts`: `PROFILE_UPGRADES`, one step per version: 1 → 2
adds traits, 2 → 3 the appearance config). Table structure changes are SQL
migrations. Appearance option ids are validated against the catalogue in
code, so adding options needs neither; changing what a field means bumps
`APPEARANCE_SCHEMA_VERSION` with an upgrade step (docs/ASSET_PIPELINE.md).

**Ownership.** Every read and write of a character is scoped by the owning
account id, which the server takes from the authenticated session (a
verified guest token), never from client input
(`server/src/profiles/profileRepository.ts`). A mismatched owner finds nothing.

**Loading stored data safely** (`ProfileService.prepare`):
- Older profile version → upgraded step by step, then saved.
- Missing or retired appearance option → replaced by the default, saved, and
  the player is told which part (hair, outfit…) changed.
- Newer profile version (written by a newer server) or an unknown version →
  loaded **read-only** with safe defaults in memory; never overwritten.
- Saved position no longer walkable (e.g. the layout changed) → spawn point.

**What is saved when:** created atomically with the account on first visit
(account + credential + character + appearance + spawn position + traits +
starting needs + wallet + starting-allowance ledger row, in one transaction);
later characters of the same profile the same way, without a new account.
Appearance on every accepted change. **Money immediately**, in its own
transaction, whenever it changes; a wage together with its shift record.
Hiring and quitting immediately. Position, needs, skills and mood events
together, in one transaction (`LifeService.saveAll`), when the player leaves,
goes back to the title screen, is evicted by a newer session or the room closes; every 30 s for every
character in the world (`PROFILE_CONFIG.autosaveIntervalMs`; needs change all
the time); and right after a completed action that gave skill XP. A seated
character is saved at the spot it stands up to.

**Not persisted (yet):** activity, seats, pending actions (including a meal
being eaten: the price is already paid, the rest of the meal is lost if the
player disconnects mid-meal), a shift in progress (it ends unpaid), greeting
cooldowns, online status, which seat you use at home.

## Replicated (`server/src/schema.ts`)

```
PlazaState
  players: Map<sessionId, PlayerState>
  seats:   Map<seatId, sessionId>   occupied or reserved seats and standing spots
  gameMinute: uint32                the world clock in game minutes (D-021);
                                    changes once per game minute

PlayerState
  name: string         the character's display name (from its profile)
  x, z: float32        metres, server-decided
  rotation: float32    radians around Y, 0 faces +Z
  moving: boolean
  connected: boolean   false during the reconnection window
  look: string         the appearance config as canonical JSON (encodeLook, < 1 KB;
                       public: everyone sees your look). One string, so a change arrives
                       as one patch and clients rebuild only the parts that changed.
  activity: string     "idle" | "sitting" | "studying" | "sketching" | "greeting"
                       | "ordering" | "eating" | "drinking" | "washing"
  seatId: string       seat or standing spot in use, else ""
  targetId: string     player being greeted while greeting, else ""
  area: string         "plaza", a room id or a home ("home/<id>") (M7c, M10)
  role: string         "" for players; a non-player character's role, e.g. "Barista" (M11)
```

**Non-player characters (M11)** are entries in the same `players` map, with
ids `npc-<id>`; nothing about them is persistent (no character row, no
needs, money or records), and the room rebuilds them from their schedules.

Character id, account id, age category, timestamps and the guest token are
**not** replicated. A player's own full profile is sent only to that player
(`profile` message).

**Private life data (M5, D-024).** Needs, mood, skills, traits, balance,
recent transactions and the job with today's shift count (M7) are **not** in
the shared state. Each player receives
only their own, as a `life` message (`LifePayload` in `shared/src/protocol.ts`):
at most every 500 ms while something visible changed, and immediately after
money changes or refusals. Other players see only the public activity
("eating", "studying"…).

## Server-only runtime

- `PlayerRuntime` (`server/src/runtime.ts`): movement intent, rate-limit
  counters, pending action (with its phase — approach, paying, active — the
  café item, request id, how much of its effect has been applied and, for a
  shift, its id, grade and wage), last greeting time per target.
- `CharacterLife` (`server/src/life/LifeSystem.ts`): the in-memory needs,
  skills, mood events, balance, recent ledger rows, job and today's shift
  count of each character in the world, the allowance day, whether a hire or
  quit is being written, and when the last `life` message was sent.
- `NpcMind` (`server/src/npc/NpcSystem.ts`, M11): per NPC, when it thinks
  next, which requests to hold back after a refusal, a wave in progress and
  greeting replies waiting to be sent. Lost on restart by design.
- `Session` (`server/src/PlazaRoom.ts`): authenticated account id, owner
  (account + character), read-only flag, last saved position, pending removal.
- `SessionRegistry`: which session currently plays each account (D-018).

## Static content (`shared/src`)

- `world.ts`: world bounds, obstacle boxes, spawn points, interactables with
  seats (sitting) and standing spots (café counter, fountain; D-026). Each
  obstacle has a stable id, a kind (what it looks like: building, arcade,
  fountain, stall, bench, planter, desk, counter, tree, lamp, chair, table,
  garden, bike-rack, noticeboard), a label (shown when tapped), its box and
  height, and optionally `facing` (rendering) and `partOf` (a chair belongs
  to its table). Each interactable has a stable id equal to its obstacle's,
  a kind that decides its actions (bench, desk, cafe, fountain, door,
  noticeboard), a menu label and its interaction points. The café counter's
  two spots behind it are tagged `use: "staff"` (M7): only for working a
  shift. Doors (M7c) are interactables of kind `door` with a link to the
  matching door in another area. The University notice board (M8) is an
  interactable of kind `noticeboard` (enrolment); desks tagged
  `lecture: true` (the lecture room's) also offer lectures and the exam.
- `areas.ts` and `interiors.ts` (M7c): the list of areas (the square and the
  indoor rooms) and the rooms' layouts (walls, furniture, the door out);
  object and seat ids are unique across all areas. On the square:
  benches 1–5, study desks 1–2, café tables 1–3 (desk rules), the café
  counter and the fountain (D-034), the hall's and library's doors (M7c)
  and the University notice board (M8).
- `appearance/`: the appearance catalogue (option ids, labels, colours, hair
  textures), the config schema with validation, look strings and look codes,
  skin-tone colour maths (OKLab), presets, the seeded randomiser and the
  visibility rules (M6).
- `profile.ts`: age categories, profile version and upgrade steps (version 2
  adds traits, version 3 the appearance config).
- `life/config.ts`: every M5 tuning value and catalogue — needs (initial
  values, rates, thresholds), offline rules, mood events, skills and XP
  curve, action effects, the café menu (`CAFE_MENU`, prices in cents),
  traits (`TRAITS`), starting balance and daily allowance, and the job
  catalogue (`JOBS`: workplace, opening hours, daily limit, grades and
  wages; M7).
- `life/work.ts`: the work rules (grade from skill levels, opening hours,
  shifts today, why a shift can't start).
- `life/config.ts` also holds the course catalogue (`COURSES`, M8: the
  fictional course, where to enrol, its room, lecture days and times, late
  entry, exam sittings and grading); `life/university.ts` holds the
  university rules (the timetable in absolute game minutes, why a lecture
  or the exam can't start, the exam grade); `life/clock.ts` gives each game
  day a weekday (Day 1 is a Monday).
- M11: `npcs.ts` holds the non-player characters (name, role, look preset,
  job, the street they arrive from, weekday and weekend blocks with their
  designated places and greeting lines) and the pure rules: the block at a
  game minute, the order of places for the hour, the greeting line, and
  `npcMayUse` (seats and spots kept free for players); `config.ts` holds
  `NPC_CONFIG` (thinking interval, retry, seats kept free, reply and wave
  timing, the tick budget).
- M10: `life/config.ts` holds the rooms (`ROOM_TYPES`: label, weekly rent),
  the furniture catalogue (`FURNITURE`: category, price, size, cosiness, a
  seat's comfort, a bed's sleep) and `HOUSING_CONFIG` (grace period, cosy
  threshold, 30 pieces); `homes.ts` the room templates (floor, the room's
  desk, fixed spots with their category) and builds a home's layout from its
  room type and placements; `life/housing.ts` the rent and cosiness rules.
  The student housing's door links to `home` (`HOME_LINK`), which the server
  resolves to the player's own home.
- M9: `life/config.ts` holds the relationship tuning (`RELATIONSHIP_CONFIG`:
  gains, daily caps, levels, history length), the chat's effects
  (`ACTION_EFFECTS.chat`, `CHAT_EFFECTS`) and the story kinds;
  `life/relationships.ts` the rules (level of a score, a moment's effect
  under the cap, the pair order); `config.ts` the safety settings
  (`SAFETY_CONFIG`: report reasons, note length, 90-day retention, limits).

## Rules to keep

- Every persistent value has a single server-side owner and is changed only by
  validated server actions.
- Separate tables per concern; no catch-all JSON column for game state. The
  appearance document is the one documented exception (D-028): purely
  cosmetic, versioned and validated as a whole.
- Currency changes are recorded as ledger transactions with an idempotency
  key, never as a client-set balance. The balance never goes below zero.
- Store the minimum personal data. Guest accounts hold no personal data beyond
  a chosen display name. A player can delete a character with all its data,
  or the whole guest profile (M12, D-046); moderation decisions (warnings,
  mutes, bans) are still to be built with sign-in (M12, D-042; see TESTING.md
  known gaps). Report
  details are deleted after 90 days (M9).
- Migrations are numbered, run in a transaction each, and have a `down`
  section. Back up before destructive migrations.
